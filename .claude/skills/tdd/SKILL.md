# TDD 스킬 (구현 단계)

이 스킬은 `CLAUDE.md`의 "구현 지침"을 실제로 적용하기 위한 절차와 도구를 정의한다.
상세설계(`detailed-design` 스킬, `ENG-SWE3-001`)의 함수 계약을 Red-Green-Refactor 방식의
TDD로 구현 코드로 옮길 때 이 기준을 그대로 따른다. 핵심 절차는
[obra/superpowers의 test-driven-development 스킬](https://github.com/obra/superpowers/blob/main/skills/test-driven-development/SKILL.md)을
Python/unittest와 이 프로젝트의 추적성·품질 게이트 요구에 맞게 옮긴 것이다.

## 1. 적용 표준과 경계

- **ISO 26262 Part 6**: 단위 수준의 방어적 프로그래밍(유효하지 않은 입력 검출, 경계값
  처리)과 오류 검출을 반영한다.
- **A-SPICE 4.1 SWE.3 → SWE.4 경계**: 이 스킬은 SWE.3(상세설계)의 함수 계약을 구현하는
  단계까지를 다루며, SWE.4(정식 단위검증)의 문서화는 §0에서 명시한 대로 범위 밖이다.
- 구현은 상세설계(`detailed-design` 스킬)가 정의한 함수 계약(입력/출력/사전조건/사후조건/
  부작용/예외/시간 제약)과 아키텍처(`architecture-design` 스킬)가 정의한 인터페이스를
  변경 없이 그대로 따른다. 계약을 바꿔야 할 필요가 있으면 구현을 진행하기 전에 사용자에게
  알린다.

## 2. 핵심 원칙 — 철칙(Iron Law)

```
실패하는 테스트 없이는 운영 코드를 작성하지 않는다
```

- 테스트를 먼저 쓴다. 실패를 지켜본다. 최소한의 코드로 통과시킨다.
- **테스트가 실패하는 것을 직접 지켜보지 않았다면, 그 테스트가 올바른 것을 검증하는지 알
  수 없다.**
- "규칙의 문구를 어기는 것은 규칙의 정신을 어기는 것이다" — "이번만 예외"는 없다.
- 테스트보다 코드를 먼저 작성했다면? **삭제하고 처음부터 다시 시작한다.** "참고용"으로
  남기지 않는다. 보면서 테스트를 "짜맞추지" 않는다. 쳐다보지 않는다. 삭제는 삭제다.
- 예외가 필요하다고 느껴지면(일회성 프로토타입, 자동 생성 코드, 설정 파일 등) 진행 전에
  사용자에게 확인한다 — 스스로 판단해서 건너뛰지 않는다.

## 3. Red-Green-Refactor 절차

구현할 DES-ID 함수 계약마다 아래 미세 주기를 반복한다.

1. 아직 구현되지 않은 함수 계약을 하나 선택한다.
2. **RED** — 그 계약(사전조건/사후조건/경계값/예외)이 지켜지지 않으면 실패하는 테스트를
   하나만 작성한다. 한 가지 동작만 검증하고, 이름에서 그 동작이 드러나야 하며, 실제 코드를
   대상으로 한다(불가피한 경우가 아니면 목(mock)을 쓰지 않는다 — §4 참고).
3. **RED 확인 (필수, 절대 생략하지 않는다)** — `python -m unittest <모듈경로> -v`로 실행해
   확인한다: (a) 테스트가 **실패**하는가(에러가 아니라), (b) 실패 메시지가 예상과 일치하는가,
   (c) 기능이 없어서 실패하는 것이지 오타 때문이 아닌가. 테스트가 이미 통과한다면 기존
   동작을 테스트하는 것이므로 테스트를 다시 작성한다. 에러가 난다면 에러를 고치고 "의도한
   이유로 실패"할 때까지 반복한다.
4. **GREEN** — 테스트를 통과시키는 **최소한의 구현**만 작성한다. 테스트가 요구하지 않는
   기능·옵션·일반화를 미리 추가하지 않는다(YAGNI).
5. **GREEN 확인 (필수)** — 다시 실행해 확인한다: 테스트 통과, 다른 테스트도 모두 통과,
   출력이 깨끗한가(에러·경고 없음). 실패하면 테스트가 아니라 코드를 고친다. 다른 테스트가
   깨지면 그 자리에서 바로 고친다.
6. §6의 품질 게이트를 실행한다. 위반이 있으면 코드를 수정하고 3~6을 반복한다 — **게이트를
   모두 통과하기 전까지 해당 함수를 완료로 표시하지 않는다.**
7. **REFACTOR** — 테스트가 계속 통과하는 상태를 유지하며 중복 제거, 이름 개선, 헬퍼 추출
   등 구조만 개선한다. 이 단계에서 새 동작을 추가하지 않는다. 이후 테스트와 게이트를 다시
   확인한다.
8. 다음 함수 계약으로 이동한다.

**흔한 합리화 — 아래처럼 생각된다면 멈추고 §2로 돌아간다:**

| 합리화 | 실제로는 |
|---|---|
| "너무 단순해서 테스트 필요 없다" | 단순한 코드도 깨진다. 테스트는 30초면 된다. |
| "나중에 테스트 쓸게" | 나중에 쓴 테스트는 바로 통과한다 — 아무것도 증명하지 못한다. 무엇을 검증해야 하는지가 아니라 이미 쓴 코드에 맞춰 테스트를 짜게 된다. |
| "이미 수동으로 확인했다" | 수동 테스트는 기록이 남지 않고, 코드가 바뀌면 재실행할 수 없다. |
| "일단 코드 남기고 테스트 먼저 쓸게" | 결국 그 코드를 "참고"해서 테스트 작성 후 코드를 맞추게 된다 — 이는 테스트-후 작성이다. |
| "테스트가 어렵다 = 설계가 아니라 그냥 복잡한 도메인이다" | 테스트하기 어려우면 사용하기도 어렵다. 인터페이스를 단순화한다. |

**위험 신호 — 발견하면 코드를 삭제하고 TDD로 다시 시작한다:** 테스트보다 코드를 먼저
작성함 / 테스트가 처음부터 바로 통과함 / 왜 실패했는지 설명할 수 없음 / "나중에" 테스트를
추가하려 함 / "이번만" 예외를 정당화하려 함.

## 4. 좋은 테스트 작성 원칙

두 가지 원칙이 좋은 테스트를 가른다:

1. **테스트마다 그것이 잡아내는 결함을 명확히 말할 수 있어야 한다** — 테스트 본문을
   쓰기 전에 "어떤 운영 코드 변경이 이 테스트를 실패하게 만드는가"에 답한다. 답할 수
   없으면 관찰 가능한 동작 중심으로 다시 설계한다. 기대값은 검증 대상 코드/헬퍼로 계산하지
   말고 손으로 도출한 리터럴을 사용한다(그렇지 않으면 항상 참인 "거울 검증"이 된다).
2. **테스트는 실제 동작을 검증해야 한다** — 목(mock) 자체의 존재/호출 여부를 검증하지
   않는다. 목으로 대체하기 전에 실제 메서드의 부작용을 모두 파악하고, 느리거나 외부에
   의존하는 부분만 목으로 만들고 테스트가 의존하는 나머지는 실제로 둔다.

세부 규칙(변이 검사, 목 사용 기준, 테스트 전용 코드 배치 등)은
[writing-good-tests.md](writing-good-tests.md)에 정리되어 있다 — 테스트를 새로 쓰거나
수정할 때, 목을 추가할 때, 테스트 헬퍼를 추가할 때는 이 문서를 함께 확인한다.

## 5. 완료 전 체크리스트

- [ ] 새로 만든 함수/메서드마다 테스트가 있다
- [ ] 각 테스트가 실패하는 것을 구현 전에 직접 지켜봤다
- [ ] 각 테스트가 예상한 이유로 실패했다(기능 없음이지 오타가 아님)
- [ ] 각 테스트를 통과시키는 최소한의 코드를 작성했다
- [ ] 모든 테스트가 통과한다
- [ ] 출력이 깨끗하다(에러·경고 없음)
- [ ] 목은 불가피한 경우에만 사용했고, 실제 동작을 검증한다
- [ ] 경계값과 오류 조건(긍정/부정 케이스)을 모두 다뤘다
- [ ] §6의 품질 게이트를 모두 통과했다
- [ ] §7의 Doxygen 태그(구현 함수·테스트 함수 모두)를 남겼고 §8의 추적 정보를 갱신했다

체크리스트를 전부 만족하지 못하면 TDD를 건너뛴 것이다 — 처음부터 다시 시작한다.

## 6. 품질 게이트와 오픈소스 도구 (CLAUDE.md "구현 지침" — 반드시 준수)

각 게이트는 **함수 단위**로 측정한다(주석 비율 포함).

| 게이트 | 기준 | 도구/명령 |
|---|---|---|
| 순환 복잡도 | 함수당 10 이하 | `radon cc -s -j <파일>` (함수별 `complexity`) |
| 함수 라인 수 | 순수 코드 라인(공백·주석 제외) 50줄 이하 | `check_quality_gates.py` (radon의 함수 범위 + tokenize 기반 계산) |
| 중복 코드 | 8줄 이상 중복 시 위반(7줄까지 허용) | `pylint --enable=duplicate-code` (`.pylintrc`의 `min-similarity-lines=8`) |
| 주석 비율 | 함수별 Doxygen 주석 줄 수 / (주석+순수 코드 줄 수) 20% 이상 | `check_quality_gates.py` |
| 식별자 | 함수명/변수명 3자 이상 + camelCase | `pylint --enable=invalid-name` (`.pylintrc`의 `*-rgx`) |

이 스킬은 `scripts/check_quality_gates.py`를 함께 제공한다.

- 사용법: `python <스킬 디렉터리>/scripts/check_quality_gates.py <파일 또는 디렉터리> [--pylintrc <스킬 디렉터리>/assets/.pylintrc] [--json]`
- 동작: 대상 경로 아래의 `*.py`를 재귀적으로 수집하되(`__pycache__` 제외), **테스트 파일
  (`test_*.py`, `*_test.py`)은 기본적으로 제외**한다(품질 게이트는 운영 코드 대상 —
  `--include-tests`로 테스트 코드까지 포함 가능). 각 함수에 대해 `radon cc`로 순환복잡도와
  줄 범위를 얻고, 그 범위를 `tokenize`로 분석해 공백/주석/코드 줄을 분류해 순수 코드 줄
  수와 주석 비율을 계산한다. 이어서 `pylint --enable=duplicate-code,invalid-name`을 한 번
  실행해 중복 코드(`R0801`)와 네이밍 위반(`C0103`)을 파일/함수/식별자 단위로 매핑한다.
- 출력: 기본은 `파일 → 함수 → 게이트: 실제값 vs 기준 → PASS/FAIL` 표 형태이며, `--json`
  옵션으로 각 항목의 리스트와 `{"result": "PASS"|"FAIL", "violations": N}` 요약을 낸다.
  모든 항목이 PASS일 때만 종료 코드 0, 하나라도 FAIL이면 종료 코드 1이며, 마지막 줄에
  `RESULT: PASS` 또는 `RESULT: FAIL (N violations)`를 출력한다. `coding` 에이전트는 이
  종료 코드로 게이트 통과 여부를 판단한다.

`.pylintrc`는 `assets/.pylintrc`로 제공하며 핵심 설정은 다음과 같다:

```
[BASIC]
function-rgx=[a-z][a-zA-Z0-9]{2,}$
variable-rgx=[a-z][a-zA-Z0-9]{2,}$
argument-rgx=[a-z][a-zA-Z0-9]{2,}$
attr-rgx=[a-z][a-zA-Z0-9]{2,}$
method-rgx=[a-z][a-zA-Z0-9]{2,}$
good-names=self,cls

[SIMILARITIES]
min-similarity-lines=8
ignore-comments=yes
ignore-docstrings=yes
ignore-imports=yes
```

`{2,}`는 "첫 글자 + 2자 이상" — 즉 식별자 3자 이상을 의미한다. `good-names`는 `self`/`cls`
로만 한정해, `i`/`x` 같은 관용적 1~2글자 변수도 3자 미만 규칙 예외로 두지 않는다(CLAUDE.md의
엄격한 규칙을 그대로 반영).

`radon`, `pylint`가 설치되어 있지 않으면 사용 전에 `pip show radon pylint`로 확인하고,
없으면 `pip install radon pylint`로 설치한다(둘 다 오픈소스 — CLAUDE.md 요건 충족).

## 7. Doxygen 주석 규약 (구현 함수 + 테스트 함수)

Python은 Doxygen의 블록 주석(`/** */`)을 쓰지 않으므로, Doxygen이 그대로 인식하는
`##`로 시작하는 줄 주석 스타일을 함수 정의 바로 위에 작성한다. 식별자는 3자 이상
camelCase로 작성한다.

**구현 함수**: `@brief`/`@param`/`@return`/`@implements` 태그를 사용한다.

```python
## @brief 두 정수를 더한다.
# @param leftValue 더할 첫 번째 정수
# @param rightValue 더할 두 번째 정수
# @return 두 정수의 합
# @implements DES-SWE-001, REQ-SWE-001
def addValues(leftValue: int, rightValue: int) -> int:
    return leftValue + rightValue
```

**테스트 함수 — 다음 세 가지를 반드시 Doxygen 주석으로 남긴다**: 테스트 목적, 사용한
기법, 긍정/부정 케이스 여부. `@brief`(목적) / `@technique`(기법) / `@case`(긍정 또는 부정)
/ `@implements` / `@testid` 태그를 사용한다.

```python
## @brief 두 정수 중 하나가 음수이면 값 오류를 발생시키는지 검증한다.
# @technique 경계값분석 (0을 기준으로 한 음수/양수 경계)
# @case 부정
# @implements DES-SWE-001, REQ-SWE-001
# @testid UT-SWE-001-02
def test_DES_SWE_001_addValues_raisesOnNegativeInput(self):
    with self.assertRaises(ValueError):
        addValues(-1, 2)
```

`@technique` 값은 `TPL-SWE4-001`의 "Technique" 열과 어휘를 맞춘다 — 예:
동등분할(Equivalence Partitioning), 경계값분석(Boundary Value Analysis),
결정테이블(Decision Table), 상태전이(State Transition), 오류추정(Error Guessing).
`@case`는 `긍정`(정상 입력이 기대한 결과를 내는지) 또는 `부정`(잘못된 입력·오류 조건을
올바르게 거부/처리하는지) 중 하나를 명시한다. 하나의 함수 계약에는 최소 긍정 케이스 1개,
경계·오류 조건이 있다면 부정 케이스도 함께 작성한다(§5 체크리스트 참고).

## 8. 추적성

- 모든 구현 함수는 Doxygen 블록에 `@implements DES-<영역>-<일련번호>, REQ-<영역>-<일련번호>`
  를 명시한다.
- 모든 테스트 메서드는 §7의 `@brief`/`@technique`/`@case`/`@implements`/`@testid
  UT-<DES-ID>-<일련번호>`(예: `UT-SWE-001-01`)를 모두 명시하고, 테스트 파일명은
  `test_<모듈명>.py`, 메서드명은 `test_<DES_ID_밑줄표기>_<검증내용>`(예:
  `test_DES_SWE_001_addValues_returnsSum`) 형식을 따른다 — 이후 SWE.4 단계에서
  `ENG-SWE4-001`의 "Test ID"/"Test Function"/"Technique" 열에 재작업 없이 옮길 수 있도록
  하기 위함이다.
- `ENG-TRC-001_양방향 요구사항 추적 매트릭스`(`TPL-TRC-001`)의 **Code** 열(10행부터)을
  구현 단위(DES-ID)별 소스 파일 경로·함수명으로 갱신한다. **SWE.4 열은 갱신하지 않는다**
  (범위 밖, §0 참고).
- 새 외부 의존성을 추가했다면 `ENG-SBOM-001`에 Package/Version/Dependency Type/SPDX/
  Evidence Type/Evidence Locator/Distribution/Remark를 기록한다.

## 9. 소스 레이아웃 기본값

아키텍처/상세설계 산출물이 소스 위치를 별도로 지정하지 않은 경우에 한해 다음을 기본값으로
사용한다: `src/<패키지>/<모듈>.py` (아키텍처 요소명 또는 DES-ID 영역을 패키지명으로 사용),
테스트는 `tests/test_<모듈>.py`로 1:1 대응시킨다.

## 10. 작업 절차

1. 입력 상세설계(`ENG-SWE3-001`, DES-ID 함수 계약)와 관련 요구사항(REQ-ID)을 확인한다.
2. §9(또는 아키텍처/상세설계가 지정한 위치)에 따라 소스 레이아웃을 정한다.
3. §3의 Red-Green-Refactor 절차를 함수 계약마다 반복한다 — RED/GREEN 확인을 생략하지
   않는다.
4. §6의 `check_quality_gates.py`로 매 반복마다 품질 게이트를 확인하고, 위반이 없을 때까지
   수정한다.
5. §7에 따라 구현 함수와 테스트 함수 모두 Doxygen 태그를 작성하고, §8에 따라 추적 태그·
   `ENG-TRC-001`의 Code 열, 필요 시 `ENG-SBOM-001`을 갱신한다.
6. §5의 체크리스트를 모두 만족하는지 확인한다.
7. 근거 없는 성능 수치, 커버리지, 매핑 관계를 지어내지 않는다. 확인이 필요한 항목은
   "확인 필요"로 표시하고 사용자에게 질문한다.
