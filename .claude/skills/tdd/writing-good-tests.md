# 좋은 테스트 작성법

**이 문서를 참고할 때**: 테스트를 새로 쓰거나 수정할 때, 목(mock)을 추가할 때, 테스트용
정리(cleanup)/헬퍼 메서드를 추가할 때.

[obra/superpowers의 writing-good-tests.md](https://github.com/obra/superpowers/blob/main/skills/test-driven-development/writing-good-tests.md)를
이 프로젝트의 Python/unittest 관례에 맞게 옮긴 것이다.

## 개요

테스트는 특정한 결함을 잡아내기 위해 존재한다. 두 가지 원칙이 모든 것을 지배한다.

```
1. 모든 테스트는 자신이 잡아내는 결함을 명확히 말할 수 있어야 한다
2. 모든 테스트는 실제 대상을 검증해야 한다
```

엄격한 TDD는 이 두 가지를 자연스럽게 만족시킨다 — 먼저 작성해 실제 코드에 대해 실패하는
것을 지켜본 테스트는 이미 "실패할 수 있음"을 증명했고, 실제 의존 대상이 느리거나 외부적일
때만 목을 쓸 자격을 얻는다.

## 원칙 1: 잡아낼 결함을 이름 붙인다

테스트 본문을 쓰기 전에 답한다: **어떤 운영 코드 변경이 이 테스트를 실패하게 만드는가 —
그리고 그 변경은 버그인가, 의도된 설계 결정인가?** 테스트는 잘못된 분기, 누락된 부작용,
잘못된 인자, 경계 조건, 깨진 계약 중 하나를 잡아낼 때 존재 가치를 얻는다.

**기대값은 독립적으로 도출한다.** 리터럴 값과 손으로 확인한 픽스처를 사용한다 — 표 기반
테스트에서 리터럴 `want` 값을 쓰는 방식을 선호한다. 검증 대상 코드(또는 그 헬퍼)로 계산한
기대값은 그 코드가 무엇을 하든 항상 통과한다.

```python
# 나쁨: 거울 검증 — 같은 빌더로 양쪽을 계산하므로 항상 참
expected = buildSearchQuery(tag="urgent")
assert buildSearchQuery(tag="urgent") == expected

# 좋음: 손으로 도출한 리터럴
assert buildSearchQuery(tag="urgent") == 'tag:"urgent"'
```

**변경 감지기를 만들지 않는다.** 의도된 설계 결정만 실패시킬 수 있는 테스트(상수 값,
정확한 메시지 문구, 내부 구조)는 리팩터링 때마다 울리고 버그에는 잠들어 있다. 그 결정에
의존하는 동작을 테스트한다 — `assert MAX_RETRIES == 5`가 아니라 "실패한 호출은 5번
재시도되고, 6번째 시도는 일어나지 않는다"를 검증한다.

**텍스트가 아니라 동작을 검증한다.** 스크립트·스킬·설정 파일이 특정 줄을 포함하는지
확인하는 것은 소스가 소스라는 것만 증명한다. 스크립트를 통제된 입력으로 실행하고 출력,
부작용, 종료 코드를 검증한다.

**프레임워크가 아니라 자신의 코드를 검증한다.** 자신의 코드가 경계에서 맺는 계약(등록하는
라우트, 만드는 쿼리, 생성하는 페이로드)을 검증한다. 상위 라이브러리의 동작은 그 라이브러리
관리자가 검증할 몫이다. 생성자, getter, 상수, 단순 위임은 값을 검증·정규화·기본값
설정·도출·강제하거나 부작용을 일으킬 때만 테스트할 가치가 있다 — 그렇지 않으면 그것에
의존하는 첫 소비자 결과를 검증한다.

### 판단 절차

```
테스트 본문을 쓰기 전에:
  이 테스트를 실패하게 만들 운영 코드 변경을 이름 붙인다.

  하나도 이름 붙일 수 없다면       -> 관찰 가능한 동작 중심으로 다시 설계
  "소스 텍스트가 바뀌었다"뿐이라면  -> 산출물을 실행하고 그 효과를 검증
  의도된 결정만 걸린다면           -> 변경 감지기다; 그 결정에 의존하는 동작을 테스트

  기대값이 검증 대상 코드 없이 도출됐는지 확인한다.
  코드의 로직/헬퍼를 재사용했다면:
    리터럴이나 손으로 확인한 픽스처로 교체
```

## 원칙 2: 실제 대상을 검증한다

**목 자체는 검증 대상이 아니다.** 목이 있으면 통과하고 없으면 실패하는 검증은 컴포넌트에
대해 아무것도 말해주지 않는다. 실제 컴포넌트의 동작을 검증한다 — 목을 검증하고 있다면
목을 제거하거나 그 검증을 삭제한다.

```python
# 좋음: 실제 동작 검증
assert response.status_code == 200

# 나쁨: 목의 존재 여부만 검증
assert mockDatabase.saveCalled
```

**적절한 수준에서 목을 사용한다.** 실제 메서드를 대체하기 전에 그 메서드의 모든 부작용을
파악한다. 느리거나 외부적인 연산만 목으로 만들고, 테스트가 의존하는 나머지는 실제로 둔다.
확신이 없으면 실제 구현으로 먼저 테스트를 돌려 실제로 무엇이 필요한지 관찰한다.

```python
# 나쁨: 목이 중복 검사가 읽는 설정 기록까지 삼켜버림
class FakeToolCatalog:
    def discoverAndCacheTools(self):
        return None  # 실제 부작용(캐시 기록)이 사라짐

# 좋음: 느린 서버 기동만 목으로 만들고, 테스트가 의존하는 설정 기록은 실제로 둠
class FakeServerLauncher:
    def start(self):
        return FakeProcess()
```

**더블(double)을 구체적으로 만든다.** 인자, 호출 횟수, 순서가 계약의 일부라면 그것을
검증한다 — 무엇이든 받아주는 가짜는 아무것도 검증하지 않는다. 각 분기(성공, 오류, 잘못된
입력)에 각자의 픽스처나 스파이를 준다.

**모의 데이터는 실제 구조를 완전히 반영한다.** 테스트가 읽는 필드만이 아니라 실제 존재하는
모든 문서화된 필드를 모의한다. 부분적인 모의는 하위 코드가 누락된 필드를 읽을 때 조용히
실패한다 — 테스트는 통과하는데 실제 연동은 깨진다.

**운영 클래스에는 운영 메서드만 둔다.** 테스트에서만 필요한 정리 코드는 테스트 유틸리티에
둔다. `destroy()` 같은 메서드를 운영 클래스에 추가하지 않는다. 자문한다: 이 메서드는
테스트에서만 호출되는가? 이 클래스가 이 자원의 생명주기를 소유하는가? 답이 아니라면 테스트
유틸리티로 옮긴다.

**복잡한 목보다 실제 컴포넌트를 우선한다.** 목 설정이 테스트 로직보다 커지거나, 목이 실제
컴포넌트에 있는 메서드를 빠뜨리거나, 목이 바뀔 때마다 테스트가 깨진다면 실제 컴포넌트를
쓰는 통합 테스트로 전환한다.

### 판단 절차

```
목이나 테스트 헬퍼를 추가하기 전에:
  실제 메서드의 부작용을 나열하고, 테스트가 의존하는 것은 실제로 둔다
  — 느리거나 외부적인 수준만 목으로 만든다.

  목 응답이 실제 구조를 완전히 반영하는지 확인한다.

  테스트에서만 호출되는 메서드는 테스트 유틸리티에 두고 운영 클래스에 두지 않는다.

  목 자체를 검증하려 하고 있는가?
    목을 제거하거나 그 검증을 삭제한다.
```

## 테스트는 구현과 함께 완성된다

TDD 주기(실패하는 테스트 → 최소 구현 → 리팩터링)가 곧 "완료"의 정의다. 그 동작이 필요로
하는 테스트만 만든다 — 사소한 코드와 사람이 읽을 설명글에는 테스트가 필요 없고, 절차를
만족시키기 위해서만 쓴 테스트는 유지보수 비용만 남긴다.

## 변이 검사(Mutation Check)

작업을 마치기 전에 머릿속으로 운영 코드를 살짝 바꿔본다. 아래와 같은 현실적인 변이마다
적어도 하나의 테스트가 실패해야 한다.

- 잘못된 상수나 인자
- 잘못된 분기 처리
- 누락된 상태 변경이나 부작용
- 빈 값이나 기본값 반환
- 0, 빈 값, None, 권한 없음, 잘못된 형식 입력에 대한 검증 누락

아무 테스트도 잡아내지 못하는 변이가 있다면, 그 동작은 보호되지 않고 있거나 그 테스트가
동어반복이라는 뜻이다.

## 빠른 참고표

| 상황 | 할 일 |
|---|---|
| 아무 테스트나 쓸 때 | 잡아낼 결함을 이름 붙인다 — 버그이지 설계 결정이 아니어야 한다 |
| 기대값을 만들 때 | 손으로 도출한다 — 검증 대상 코드로 계산하지 않는다 |
| 스크립트나 문서를 테스트할 때 | 실행하거나 소비자를 통해 검증한다 — 텍스트를 grep하지 않는다 |
| 의존성을 테스트하고 싶을 때 | 그 라이브러리의 문서화된 동작이 아니라 자신의 경계 계약을 테스트한다 |
| 목의 요소를 검증하려 할 때 | 실제 컴포넌트를 검증하거나 목을 제거한다 |
| 메서드를 목으로 만들려 할 때 | 부작용을 먼저 파악하고, 느리거나 외부적인 수준만 목으로 만든다 |
| 목 응답을 만들 때 | 실제 구조를 완전히 반영한다 |
| 테스트 전용 정리 코드가 필요할 때 | 테스트 유틸리티에 둔다 |
| 목 설정이 커질 때 | 실제 컴포넌트를 쓰는 통합 테스트로 전환한다 |
| 테스트 파일을 마칠 때 | 변이 검사를 수행한다 |

## 경고 신호

- 설정과 검증이 같은 객체를 공유해 항상 같음이 보장됨
- 예외나 크래시, 셀렉터 누락으로만 테스트가 실패할 수 있음
- 의도된 모든 변경에서 실패하고 실수로 인한 손상에는 실패하지 않음
- 기대값이 반복문·빌더·헬퍼 뒤에 숨어 있음
- 소스 텍스트를 grep하거나, 제거된 심볼이 계속 없는지만 검증함
- 프레임워크만 남아도 여전히 통과할 테스트임
- 커버리지만을 위해 존재하고 부작용·결과를 검사하지 않음
- `*-mock` 같은 테스트 ID를 검증하거나, 목을 제거하면 실패함
- 어떤 메서드가 테스트 파일에서만 호출됨
- 목 설정이 테스트의 절반 이상을 차지하거나, 왜 그 목이 필요한지 설명할 수 없음
- "혹시 몰라서" 목을 사용함
