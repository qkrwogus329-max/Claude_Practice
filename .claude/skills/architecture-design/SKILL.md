# 아키텍처 설계 스킬

이 스킬은 소프트웨어 아키텍처를 설계하거나 검토할 때 반드시 따라야 하는 원칙, 후보 제안
절차, 산출물 템플릿을 정의한다.

## 0. 산출물 템플릿 (필수 준수)

이 저장소의 `WP_Templates/Engineering/SoftwareArchitecturalDesign/` 에 있는 템플릿을
**그대로** 따른다. 다른 구조를 임의로 만들지 않는다.

- `TPL-SWE2-001_SW 아키텍처 설계서 템플릿.docx` — 문서 본문 구조 (§5 참고)
- `TPL-SWE2-002_SW 아키텍처 UML 템플릿.drawio` — 요소/액터/인터페이스/의존관계를 표현하는
  draw.io 다이어그램 골격. 안내 도형(가이드 텍스트)을 삭제하고 실제 요소·인터페이스·추적 ID로
  채운다.

새 산출물을 만들 때는 템플릿 파일을 복사한 뒤 파일명을 실제 산출물 ID로 바꾸고
(`WP_Templates/Engineering/README.md`의 규칙), 프로젝트·버전·베이스라인 정보를 채운다.
`WP_Templates/PRC-TPL-001_표준 산출물 양식 등록부.xlsx`에 따른 실제 산출물 ID:

- SW 아키텍처 설계서 → `ENG-SWE2-001_SW 아키텍처 설계서.docx`
- SW 아키텍처 UML 원본 → `ENG-SWE2-002_SW 아키텍처 UML 원본.drawio`

문서 ID(`ENG-SWE2-001` 등)와 개별 아키텍처 요소 ID(`ARC-<영역>-<일련번호>`)는 서로 다른
식별자이며 혼동하지 않는다.

> **교육용 자료 안내**: 이 템플릿들은 SW 품질교육용 자료로 저작권이 Synetics에 있다
> (README.md 명시). 또한 `PRC-TPL-001` 등록부는 이 저장소가 교육용 가상 프로젝트
> (VJ-ECL-2026)이며, PC/SIL·Web 증거만 다루고 **HIL, 실차, 시스템 시험, 공식 A-SPICE
> 심사, ISO 26262 준수, 인증 또는 ASIL 달성을 주장하지 않는다**고 명시한다. 이 스킬로
> 작성하는 아키텍처 산출물도 실제 인증·준수를 주장하지 않으며, 표준의 구조와 원칙을
> 학습·적용하는 목적임을 문서에 함께 남긴다. 이 템플릿 자료를 저장소 밖으로 배포·게시하지
> 않는다.

## 1. 적용 표준과 필수 원칙

- **ISO 26262 Part 6**: 소프트웨어 아키텍처 설계 요구사항 — 요소 분해, 계층 구조, 오류
  검출/격리, 안전 메커니즘, 리소스 사용(스택/메모리/실행시간) 고려, 프리덤 프롬 인터피어런스
  (Freedom From Interference)를 필요 시 반영한다.
- **A-SPICE 4.1 SWE.2**: 아키텍처가 요구사항을 충족하고, 요소 간 인터페이스가 일관되며,
  요구사항이 아키텍처 요소에 할당·추적 가능해야 한다.
- **응집도/결합도 (반드시 준수)**: 각 컴포넌트는 하나의 명확한 책임에 집중해 **높은 응집력**을
  가져야 하고, 컴포넌트 간에는 **낮은 결합도**를 유지해야 한다. 순환 의존, 과도한 공유 상태,
  숨겨진 전역 의존은 금지한다.
- **변경 유연성**: 요구사항 변경이 예상되는 지점(가변점)을 식별하고, 해당 지점을 인터페이스나
  플러그인 구조로 분리해 변경의 파급 범위를 최소화한다.
- **SOLID 원칙**: 컴포넌트/모듈 설계에 아래를 적용한다.
  - SRP(단일 책임): 컴포넌트는 하나의 변경 이유만 가진다.
  - OCP(개방-폐쇄): 확장은 새 구현 추가로, 기존 코드 수정 없이 가능해야 한다.
  - LSP(리스코프 치환): 인터페이스의 구현체는 상호 대체 가능해야 한다.
  - ISP(인터페이스 분리): 클라이언트가 쓰지 않는 기능에 의존하지 않도록 인터페이스를 분리한다.
  - DIP(의존성 역전): 상위 컴포넌트는 하위 구현이 아니라 추상(인터페이스)에 의존한다.
- **인터페이스 기반 통신 (반드시 준수)**: 모든 컴포넌트는 명시적으로 정의된 인터페이스
  (제공/요구 인터페이스, 시그니처, 데이터 계약, 오류 계약)를 가져야 하며, 컴포넌트 간
  통신은 **오직 이 인터페이스를 통해서만** 이루어진다. 컴포넌트 내부 구현이나 내부 상태에
  직접 접근하는 통신은 금지한다.

## 2. 아키텍처 후보 제안 절차 (필수)

아키텍처를 설계할 때는 **바로 하나로 확정하지 않고**, 프로젝트 맥락에 맞는 후보를 2~4개
제안하여 사용자가 선택하게 한다.

1. 요구사항과 제약(실시간성, 자원 제약, 안전 등급, 변경 빈도가 높은 영역 등)을 파악한다.
2. 아래 표를 참고해 맥락에 맞는 후보 아키텍처 스타일을 선정한다(전부 나열할 필요는 없다).
3. 각 후보에 대해 **개요, 이 프로젝트에 적용했을 때의 장단점(응집도/결합도, 변경 유연성,
   SOLID 적합성, 실시간성/자원 제약과의 궁합)**을 간단히 비교표로 제시한다.
4. 사용자에게 후보 중 하나를 선택하도록 요청한다(`AskUserQuestion` 방식으로 질문). 사용자가
   선택하거나 요구사항을 조정하기 전까지 §5 이하의 상세 설계로 진행하지 않는다.

| 후보 스타일 | 적합한 상황 | 주의점 |
|--------------|--------------|--------|
| 계층형(Layered) | 관심사 분리가 뚜렷하고 상하위 계층 호출 방향이 단순한 경우 | 계층 간 우회 호출(레이어 스킵) 금지 규칙 필요 |
| 컴포넌트 기반(AUTOSAR SWC 유사) | 자동차 ECU 소프트웨어처럼 재사용 가능한 기능 단위로 나눌 수 있는 경우 | 포트(제공/요구 인터페이스) 정의가 핵심 |
| 포트-어댑터(Hexagonal) | 핵심 로직을 하드웨어/외부 시스템 변경으로부터 격리해야 하는 경우 | 어댑터 계층 증가로 초기 설계 비용 상승 |
| 이벤트 기반(Event-Driven/Pub-Sub) | 비동기 이벤트 처리, 컴포넌트 간 낮은 결합이 특히 중요한 경우 | 이벤트 순서/타이밍 보장, 디버깅 난이도 고려 |
| 파이프-필터(Pipe-and-Filter) | 데이터가 순차적으로 여러 처리 단계를 거치는 경우 | 단계별 처리 지연이 실시간 요구를 해칠 수 있음 |

## 3. 컴포넌트 설계 규칙

- 각 컴포넌트에 고유 ID(`ARC-<영역>-<일련번호>`, 예: `ARC-SWE-001`)를 부여한다.
- 컴포넌트별 책임, 입력/출력, 상태, 오류 처리를 명시한다(템플릿 §4 대응).
- 정적 의존성은 방향성을 명시하고 순환 의존을 금지한다(템플릿 §5 대응).
- 인터페이스는 고유 ID(`IF-<영역>-<일련번호>`, 예: `IF-SWE-001`)와 제공자, 사용자, 데이터,
  호출 조건, 시간 제약, 오류 계약을 명시한다(템플릿 §6 대응). 내부 인터페이스(§6.1)와
  외부 인터페이스(§6.2)를 구분한다. 이 IF-ID는 이후 `integration-testing` 스킬의 시험
  근거(테스트 베이시스)로 그대로 참조된다.

## 4. 통합 순서 정의 (필수)

컴포넌트 의존성 그래프를 기준으로 통합 순서를 정의한다(템플릿 §11 대응).

1. 정적 의존성(§3)을 바탕으로 의존성 그래프를 그린다.
2. 다른 컴포넌트에 의존하지 않는(또는 의존이 가장 적은) 하위/공통 컴포넌트부터 통합한다
   (상향식 기본 원칙). 실시간성·안전 등급상 특정 컴포넌트를 먼저 검증해야 한다면 그 근거를
   명시하고 순서를 조정한다.
3. 아직 통합되지 않은 의존 대상은 스텁(Stub)/드라이버(Driver)로 대체해 인터페이스 계약을
   검증한다.
4. 각 통합 단계에서 검증할 인터페이스와 회귀 시험 범위를 함께 정의한다.
5. 통합 순서, 스텁/드라이버 사용 계획, 회귀 범위를 표로 정리한다.

## 5. 산출물 구조 (TPL-SWE2-001 템플릿 그대로)

1. 목적 및 적용범위 (1.1 목적 / 1.2 적용범위 / 1.3 적용 경계)
2. 아키텍처 설계 원칙 — §1의 원칙(응집도/결합도, SOLID, 인터페이스, 오류격리, 변경용이성)을
   이 프로젝트에 어떻게 적용했는지 기술
3. 논리 아키텍처 (3.1 아키텍처 요소 / 3.2 관계와 제약) — §2에서 선택된 아키텍처 스타일을 반영
4. 컴포넌트 책임 (§3 대응)
5. 정적 의존성 (§3 대응)
6. 인터페이스 명세 (6.1 내부 인터페이스 / 6.2 외부 인터페이스, §1의 인터페이스 통신 원칙 반영)
7. 동적 동작 — 주요 시나리오의 호출 순서/데이터 흐름 (시퀀스/활동 다이어그램)
8. 상태 전이 — 상태, 전이 이벤트, 가드, 금지 전이
9. 오류 격리와 안전 동작 — ISO 26262 관점의 오류 감지/전파 차단/안전 상태
10. 품질속성 분석 — 성능, 신뢰성, 유지보수성 등 ISO 25010 관점 시나리오와 설계 대응
11. 통합 전략 — §4의 통합 순서, 스텁/드라이버, 회귀 범위
12. 요구사항 할당 — SW 요구사항(REQ-ID)을 아키텍처 요소(ARC-ID)에 매핑, 누락/중복 확인
13. 자원 및 배포 경계 — 실행 노드, 프로세스, 메모리/CPU/저장소, 배포 제약
14. 추적성 — 요구사항 ↔ 아키텍처 요소 ↔ 상세설계 ↔ 통합 검증 간 연결
15. 참고자료 — 입력 요구사항, 적용 표준, 설계 결정 기록

각 다이어그램은 `TPL-SWE2-002_SW 아키텍처 UML 템플릿.drawio` 골격을 복사해 요소·인터페이스·
추적 ID를 채워 작성한다.

## 6. 추적성

- `requirements-analysis` 스킬에서 부여한 `REQ-<영역>-<일련번호>`를 그대로 참조한다.
- 아키텍처 요소에는 `ARC-<영역>-<일련번호>` ID를 부여하고, §12 요구사항 할당표에서
  REQ-ID ↔ ARC-ID 매핑을 기록한다.
- `ENG-TRC-001_양방향 요구사항 추적 매트릭스`(`TPL-TRC-001`)의 **Architecture** 열에
  아키텍처 요소 매핑을 채운다. 이 매트릭스는 Upper Req/SW Req/Architecture/Detailed
  Design/Code/SWE.4/SWE.5/SWE.6/Coverage 열로 구성되며, 데이터는 10행부터 입력한다.

## 7. 작업 절차

1. 입력 요구사항(REQ-ID 포함)과 제약을 파악한다.
2. §2에 따라 아키텍처 후보를 제안하고 사용자 선택을 받는다.
3. 선택된 스타일로 §3의 컴포넌트/인터페이스를 설계한다(응집도/결합도, SOLID, 인터페이스
   통신 원칙 준수 여부를 스스로 점검).
4. §4에 따라 통합 순서를 정의한다.
5. §5의 템플릿 구조로 문서를 작성하고, §6에 따라 추적성을 반영한다.
6. 근거 없는 수치나 관계를 지어내지 않는다 — 확인이 필요하면 "확인 필요"로 표시하고
   사용자에게 질문한다.
