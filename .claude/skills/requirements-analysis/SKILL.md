# 요구사항 분석 스킬

이 스킬은 `CLAUDE.md`의 "요구사항 작성 정책"을 실제로 적용하기 위한 세부 기준과 절차를
제공한다. 요구사항을 새로 작성하거나 기존 요구사항을 검토할 때 이 기준을 그대로 따른다.

> 원칙을 학습·적용하는 목적임을 문서에 함께 남긴다. 이 템플릿 자료를 저장소 밖으로
> 배포·게시하지 않는다.

## 1. 적용 표준

- **ISO 26262**: 안전 관련 요구사항의 경우 ASIL 분류, 안전 목표와의 연계를 명시한다
  (템플릿 §4.2 "안전 관련 SW 요구사항" 대응).
- **A-SPICE 4.1 SWE.1**: 요구사항은 식별·상태·품질판정 규칙을 가지고, 하향 할당과 검증
  계획이 연결되어야 한다. CL2 관점(성과 관리/산출물 관리)의 감사는 `aspice-auditor` 스킬
  기준을 참고한다.

## 2. 기능 요구사항 — Use Case 기반 UML 표현

기능 요구사항은 `TPL-SWE1-002` Use Case 명세서로 상세화하고, `TPL-SWE1-003` Use Case
다이어그램으로 표현한다.

- Use Case 명세서(§6 구조)에는 액터, 사전조건/트리거, 기본 흐름, 대안 흐름, 예외 흐름,
  사후조건을 모두 작성한다.
- Use Case 다이어그램은 `TPL-SWE1-003`의 안내 도형(시스템 경계, 액터, 요소, 관계)을 삭제하고
  실제 시스템 경계·주 액터·보조 액터·Use Case·관련 요구사항 ID로 채운다.
- 하나의 요구사항이 여러 흐름/조건을 가지면 대안·예외 흐름으로 분리하고, 요구사항 문서의
  기능 요구사항 항목과 상호 참조한다.
- 아키텍처/상세설계 단계에서 필요한 Sequence/State Machine 등 추가 UML/SysML 다이어그램은
  `architecture-design` 스킬(§2, `TPL-SWE2-002`)에서 다룬다 — 요구사항 단계에서는 Use Case
  중심으로 표현한다.

## 3. 비기능 요구사항 — ISO 25010 + 검증방안

비기능 요구사항은 요구사항 명세서 §7 "비기능 및 환경 제약"에 작성하며, ISO 25010의 8대
품질 특성 중 하나 이상으로 분류한다.

| 품질 특성 | 예시 관심사 |
|-----------|-------------|
| 기능 적합성 (Functional Suitability) | 완전성, 정확성, 적절성 |
| 성능 효율성 (Performance Efficiency) | 응답시간, 처리량, 자원 사용률 |
| 호환성 (Compatibility) | 공존성, 상호운용성 |
| 사용성 (Usability) | 학습 용이성, 오류 방지, 접근성 |
| 신뢰성 (Reliability) | 성숙성, 가용성, 결함 허용, 복구성 |
| 보안성 (Security) | 기밀성, 무결성, 부인방지, 책임추적성, 인증 |
| 유지보수성 (Maintainability) | 모듈성, 재사용성, 분석/수정/시험 용이성 |
| 이식성 (Portability) | 적응성, 설치 용이성, 대체 용이성 |

각 비기능 요구사항에는 **실행 가능한 검증 방안**을 함께 제시한다. 검증 방안은 다음 중
하나에 해당하는 구체적·측정 가능한 방법이어야 한다: **시험(측정 가능한 수치 기준의 테스트)
/ 분석(계산·시뮬레이션) / 검사(코드·문서 리뷰) / 데모(시연)**. 이 저장소는 PC/SIL·Web
증거만 다루므로(§0 안내), HIL·실차 등 이 환경에서 실행할 수 없는 검증 방법은 제시하지 않는다.

- **허용**: "정상 부하(초당 100건 요청) 조건에서 API 응답시간은 200ms 이하여야 한다.
  (검증: PC/SIL 환경에서 부하 테스트 도구로 측정)"
- **금지**: "시스템은 충분히 빨라야 한다", "사용자가 만족해야 한다" 같이 측정 불가능하거나
  주관적인 표현과, 현재 기술/환경으로 실행할 수 없는 검증 방법(예: 보유하지 않은 HIL 장비를
  전제로 한 검증)은 제시하지 않는다.

## 4. 명확성 확보 — EARS 구문 사용

모든 요구사항은 **EARS(Easy Approach to Requirements Syntax)** 패턴 중 하나로 작성하여
모호함을 줄인다.

- 유비쿼터스: "`<시스템>`은 항상 `<요구사항>`을 만족해야 한다."
- 이벤트 구동: "`<트리거>`가 발생하면, `<시스템>`은 `<응답>`을 수행해야 한다."
- 상태 구동: "`<상태>`인 동안, `<시스템>`은 `<응답>`을 수행해야 한다."
- 옵션 기능: "`<기능>`이 포함된 경우, `<시스템>`은 `<응답>`을 수행해야 한다."
- 원치 않는 동작: "`<원치 않는 조건>`이 발생하면, `<시스템>`은 `<대응>`을 수행해야 한다."

추가 체크리스트(템플릿 §2.2 "품질 판정 기준" 대응): 하나의 요구사항에는 하나의 요구사항만
담는다(원자성) / "그리고", "또는"으로 여러 요구사항을 묶지 않는다 / 정의되지 않은 용어를
쓰지 않는다(용어집 참고, §6) / 수동태 대신 능동태를 쓴다 / 정량적 기준을 사용한다.

## 5. 요구사항 명세서 구조 (TPL-SWE1-001 템플릿 그대로)

1. 목적 및 적용범위 (1.1 목적 / 1.2 적용범위 / 1.3 적용 경계)
2. 요구사항 작성 및 판정 규칙 (2.1 식별 및 상태 규칙 / 2.2 품질 판정 기준 — §4의 EARS/체크리스트 반영)
3. 상태와 우선순위
4. 기능 및 안전 관련 SW 요구사항 (4.1 기능 요구사항 / 4.2 안전 관련 SW 요구사항 — ISO 26262 ASIL/안전목표 연계)
5. 입력 데이터 사전 — 입력 신호/데이터 명칭, 자료형, 단위, 범위, 유효성, 오류 처리
6. 외부 인터페이스 요구 — 외부 시스템/하드웨어/통신/사용자 인터페이스별 입력·출력·오류 계약
7. 비기능 및 환경 제약 — §3의 ISO 25010 분류 + 검증 방안
8. 분석 결과와 가정 — 가정, 의존성, 상충 사항, 미결정 항목
9. 하향 할당 및 검증 계획 — 요구사항별 설계 할당 대상, 검증 수준/방법, 계획된 증거
10. 범위 밖 주장 — 이 문서와 증거만으로 주장할 수 없는 시험 수준/인증/적합성 범위(§0 disclaimer 반영)
11. 추적성 — §7 추적 매트릭스와 연결 규칙
12. 참고자료 — 적용 표준, 고객 입력, 법규, 기술 자료

각 요구사항 항목은 최소 다음 정보를 포함한다: ID(`REQ-<영역>-<일련번호>`), 출처, 조건,
동작, 정량 기준, 검증 방법, 상태.

## 6. Use Case 명세서 구조 (TPL-SWE1-002 템플릿 그대로)

1. 목적 및 적용범위
2. 액터와 시스템 경계
3. Use Case 목록 — ID, 명칭, 목적, 주 액터, 관련 요구사항, 우선순위
4. Use Case 상세 (4.1 기본 정보 / 4.2 사전조건과 트리거 / 4.3 기본 흐름 / 4.4 대안 흐름 /
   4.5 예외 흐름 / 4.6 사후조건)
5. 비대상 시나리오 — 현재 범위에서 다루지 않는 액터/기능/시험 수준
6. 추적성 — 상위 입력, SW 요구사항, 설계, 검증 항목과의 연결
7. 참고자료

## 7. 추적성 확보 방안

- 모든 요구사항에 고유 ID `REQ-<영역>-<일련번호>`를 부여한다.
- `TPL-TRC-001`(`ENG-TRC-001_양방향 요구사항 추적 매트릭스`)의 실제 열 구조를 그대로
  사용한다: **Upper Req(상위요구) | SW Req(SW요구) | Architecture(아키텍처) | Detailed
  Design(상세설계) | Code(코드) | SWE.4(단위시험) | SWE.5(통합시험) | SWE.6(검증) |
  Coverage(커버리지)**. 데이터는 10행부터 입력한다(1~9행은 문서 통제/헤더 영역).
- 요구사항 작성 시 최소 "Upper Req"와 "SW Req" 열을 채우고, 이후 설계·구현·시험 산출물이
  나올 때마다 해당 열(Architecture/Detailed Design/Code/SWE.4/SWE.5/SWE.6/Coverage)을
  갱신한다. 이 매트릭스 갱신은 요구사항 작업 완료의 일부이며, 갱신 없이 완료 처리하지 않는다.
- 용어집(Glossary)을 유지하여 동일 개념에 항상 같은 용어를 사용한다.

## 8. 일관성 확보 방안

- 새 요구사항 작성/수정 시 동일 대상에 대해 기존 요구사항과 상충하는 값·조건이 없는지
  교차 검토한다(예: 동일 파라미터에 대한 서로 다른 한계값).
- 용어집(§7)에 없는 새 용어를 도입할 경우 용어집에 추가하고, 기존 요구사항의 유사 용어와
  충돌하지 않는지 확인한다.
- 단위(ms, %, 초당 건수 등)와 표현 형식을 문서 전체에서 통일한다.

## 9. 작업 절차

1. 입력 자료(이해관계자 요구, 상위 요구사항, 기존 산출물)를 파악한다.
2. §5의 템플릿 구조에 맞춰 요구사항 초안을 작성하고 §7에 따라 ID를 부여한다.
3. 기능/비기능으로 분류한다.
   - 기능 요구사항: §2에 따라 `TPL-SWE1-002` Use Case 명세서와 `TPL-SWE1-003` 다이어그램을
     작성한다.
   - 비기능 요구사항: §3에 따라 ISO 25010 특성으로 분류하고 실행 가능한 검증 방안을 정한다.
4. §4의 EARS 패턴과 체크리스트로 명확성을 검토하고 문장을 다듬는다.
5. §8에 따라 기존 요구사항과의 일관성을 교차 검토한다.
6. §7에 따라 `ENG-TRC-001` 추적성 매트릭스를 갱신한다(신규 항목 추가 또는 기존 매핑 수정).
7. 완성된 요구사항(과 Use Case·검증방안·추적정보)을 §5/§6 문서 구조로 정리한다.

증거나 근거 없이 임의로 검증 기준·수치·추적 관계를 지어내지 않는다. 확인이 필요한 항목은
"확인 필요"로 표시하고 사용자에게 질문한다.
