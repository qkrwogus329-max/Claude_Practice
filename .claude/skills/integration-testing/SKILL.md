# 소프트웨어 통합시험 스킬 (SWE.5)

이 스킬은 아키텍처 설계서에서 정의한 컴포넌트를 인터페이스를 통해 통합하면서, 정의된
통합 순서대로 컴포넌트 간 상호작용을 검증하는 통합시험을 설계·실행하기 위한 기준을
정의한다. 시스템/HIL/실차 통합은 다루지 않는다 — 이 저장소는 SW-SW 통합(PC/SIL·Web
환경)만을 대상으로 한다.

## 1. 적용 표준 — ISO 26262 Part 6 통합시험 기법

각 통합시험 케이스는 아래 기법 중 하나 이상에 근거해 설계하고, 어떤 기법을 왜 선택했는지
`TPL-SWE5-001` §7 "시험 설계기법"에 근거를 기록한다.

| 기법 | 내용 | 적용 기준 |
|---|---|---|
| 요구사항 기반 시험 | 할당된 SW 요구사항(REQ-ID)이 인터페이스를 통해 올바르게 충족되는지 검증 | 모든 통합 항목에 기본 적용 |
| 인터페이스 시험 | 인터페이스(IF-ID)의 데이터 형식, 호출 조건, 시간 제약, 오류 계약이 지켜지는지 검증 | 모든 인터페이스에 기본 적용 |
| 결함 주입 시험 | 의도적으로 잘못된 입력/오류 조건을 주입해 오류 검출·격리 동작을 검증 | 안전 관련(ASIL 할당) 인터페이스, 방어적 설계가 있는 인터페이스 |
| 자원 사용량 시험 | 통합된 컴포넌트의 메모리/CPU/실행시간 등 자원 사용이 설계 한계 내인지 검증 | 자원 제약이 명시된 통합 항목 |
| 성능 시험 | 처리시간·처리량 등 성능 요구가 인터페이스 조합에서도 충족되는지 검증 | 성능 요구사항(NFR)이 있는 통합 항목 |
| Back-to-back 비교 시험 | 모델(있는 경우)과 코드의 출력을 동일 입력에 대해 비교 | 모델 기반 설계 산출물이 있는 경우에 한함 — 없으면 적용하지 않고 그 사유를 기록 |

## 2. 시험 근거(테스트 베이시스)

- **인터페이스**: 아키텍처 설계서(`ENG-SWE2-001`) §6 "인터페이스 명세"에 정의된 IF-ID
  (제공자, 사용자, 데이터, 호출 조건, 시간 제약, 오류 계약)를 그대로 시험 근거로 쓴다.
  통합시험 케이스는 반드시 하나 이상의 IF-ID를 참조해야 하며, 인터페이스와 무관한 임의의
  케이스를 만들지 않는다.
- **통합 순서**: 아키텍처 설계서 §11 "통합 전략"에서 정의한 통합 순서를 그대로 따른다.
  이 스킬(`TPL-SWE5-001` §3 "통합 항목과 순서")은 그 순서를 실행 가능한 시험 계획으로
  세분화하는 것이며, 근거 없이 순서를 재배열하지 않는다. 순서를 바꿔야 할 필요가 있으면
  사유를 기록하고 `architecture-designer`/사용자에게 알린다.
- 상세설계(DES-ID)와 구현 코드가 있다면 인터페이스가 실제 함수 시그니처와 일치하는지도
  함께 확인한다.

## 3. 구조적 커버리지 목표 (필수 100% — ISO 26262-6 구조적 커버리지 지표)

- **함수 커버리지(Function Coverage)**: 통합 대상 소스의 모든 함수/메서드가 통합시험
  실행 중 최소 1회 호출되어야 한다.
- **Call 커버리지(Call Coverage)**: 정적 콜그래프(호출자→호출대상)의 모든 간선이 통합시험
  실행 중 최소 1회 실행되어야 한다.
- 두 지표 모두 **100% 달성이 필수**다. 100% 미만이면 시험 케이스를 추가해 보완하기 전까지
  통합시험을 완료로 표시하지 않는다.
- **테스트 성공률도 100%**여야 한다(CLAUDE.md "통합시험 지침") — 실패하는 통합시험
  케이스를 남긴 채 완료로 표시하지 않는다.

이 스킬은 `scripts/measure_call_coverage.py`를 함께 제공한다.

- 사용법: `python <스킬 디렉터리>/scripts/measure_call_coverage.py --src <운영 코드
  디렉터리> --tests <통합시험 코드 디렉터리> [--extra-edges <json>] [--json]`
- 동작: `--src` 아래 소스를 정적 분석(ast)해 함수 집합과 호출 간선(같은 모듈 내 직접 호출,
  `self`/`cls` 메서드 호출, `import`로 연결된 모듈 간 호출)을 구성한다. `--tests` 아래
  unittest 테스트를 discover로 찾아 실행하는 동안 `sys.setprofile`로 실제 호출을
  추적해 정적 그래프와 비교한다.
- **정적 분석의 한계**: 동적 디스패치(타입을 알 수 없는 객체의 메서드 호출)는 해석하지
  못한다. 아키텍처 §6에 정의된 인터페이스 중 이 스크립트가 놓친 호출 관계가 있다면
  `--extra-edges`로 `[{"caller": "<모듈>::<함수>", "callee": "<모듈>::<함수>"}, ...]`
  형식의 JSON을 만들어 보완한다. **이 스크립트의 결과만 맹신하지 않는다** — 아키텍처
  §6 인터페이스 목록과 대조해 스크립트가 놓친 호출이 없는지 확인한다.
- 출력: 함수/Call 커버리지 비율과 미실행 함수·간선 목록, 테스트 실행 결과. `--json`으로
  구조화된 결과를 얻을 수 있다. 두 커버리지가 모두 100%이고 테스트가 전부 통과할 때만
  종료 코드 0.

## 4. 시험 케이스 설계 절차

아키텍처의 통합 순서(§2)에 따라 단계별로 진행한다.

1. 해당 단계에서 새로 통합되는 컴포넌트와 그 인터페이스(IF-ID)를 식별한다.
2. 아직 통합되지 않은 의존 대상은 아키텍처 §11에서 계획한 스텁/드라이버로 대체한다.
3. §1의 기법(기본: 요구사항 기반 시험 + 인터페이스 시험)으로 각 인터페이스의 긍정
   케이스(정상 데이터/호출 조건)와 부정 케이스(경계값, 잘못된 입력, 오류 계약 위반)를
   작성한다.
4. §3의 스크립트로 함수/Call 커버리지를 확인한다. 갭이 있으면 그 함수/간선을 실행하는
   케이스를 추가한다(우선 요구사항 기반/인터페이스 시험으로 채우고, 안전 관련 인터페이스는
   결함 주입 시험을 추가한다).
5. `TPL-SWE5-001` §5 "진입 및 종료 기준"에 정의한 기준(예: 커버리지 100%, 실패 0건)을
   만족하는지 확인한 뒤 다음 통합 단계로 이동한다.
6. 변경이 발생하면 §9 "회귀 전략"에 따라 영향받는 케이스를 다시 실행한다.

## 5. 통합전략 및 시험 명세서 구조 (TPL-SWE5-001 템플릿 그대로)

1. 목적 및 적용범위 (1.1 목적 / 1.2 적용범위 / 1.3 적용 경계)
2. 통합 원칙 — 통합 단위, 단계, 위험 우선순위, 반복 가능성, 실패 격리 원칙
3. 통합 항목과 순서 — 아키텍처 §11 통합 순서를 세분화(ID/선행조건/의존성/순서/담당/베이스라인)
4. 환경 및 형상 — 도구, 실행환경, SW 버전, 시험 데이터, 형상 식별
5. 진입 및 종료 기준 — 각 단계의 시작/중단/재개/완료 판정 기준(커버리지 100% 포함)
6. 통합시험 케이스 요약 — 시험 ID, 추적 대상, 기대결과, 자동화 여부 요약
7. 시험 설계기법 — §1 기법의 선정 근거와 적용 대상
8. 실행 및 결과 기록 규칙 — 실행 식별자, 시각, 환경, 결과, 증거 위치, 결함 연결
9. 회귀 전략 — 변경 영향에 따른 회귀 범위, 자동 실행, 결과 비교
10. 실패 및 편차 처리 — 분류, 보고, 재시험, 승인 절차
11. 추적성과 보고 — 아키텍처 인터페이스, 시험 케이스, 결과, 결함, 보고서 연결
12. 적용 한계 — 이 통합시험으로 확인하지 못하는 시스템/HIL/실차/양산 범위(§0 disclaimer 반영)
13. 추적성 — §8 매핑
14. 참고자료 — 아키텍처, 상세설계, 검증 계획, 환경 정의, 도구 자료

## 6. 통합시험 케이스 구조 (TPL-SWE5-002 템플릿 그대로)

`Integration Cases` 시트: Test ID | Trace | Integration Item | Stimulus | Expected
Result | Technique | Automation. 데이터는 10행부터 입력한다. `Trace` 열에는 IF-ID/

## 7. 통합시험 결과서 구조 (TPL-SWE5-003 템플릿 그대로)

- `Integration Results` 시트: Test ID | Trace | Result | Actual Result | Evidence
  Locator | Defect ID | Disposition
- `Run Summary` 시트: Run ID | Date | Baseline | Environment | Planned | Pass | Fail |

## 8. Doxygen 주석 규약 (통합시험 코드)

통합시험을 Python unittest 코드로 작성할 때는 `tdd` 스킬과 동일한 Doxygen 규약을
따르되, 인터페이스 근거를 추가한다: `@brief`(목적) / `@technique`(§1의 기법명) /
`@case`(긍정 또는 부정) / `@interface`(IF-ID) / `@implements`(ARC-ID, REQ-ID) /
`@testid`(IT-ID).

```python
## @brief 센서 인터페이스가 잘못된 범위값을 전달하면 오류 계약대로 예외를 발생시키는지 검증한다.
# @technique 인터페이스 시험, 결함 주입 시험
# @case 부정
# @interface IF-SWE-001
# @implements ARC-SWE-001, REQ-SWE-001
# @testid IT-SWE-001-02
def test_IF_SWE_001_sensorInterface_rejectsOutOfRangeValue(self):
    with self.assertRaises(ValueError):
        sensorInterface.readValue(999)
```

## 9. 추적성

- 통합시험 케이스에는 `IT-<영역>-<일련번호>` ID를 부여한다(예: `IT-SWE-001-01`).
- `ENG-TRC-001_양방향 요구사항 추적 매트릭스`(`TPL-TRC-001`)의 **SWE.5** 열(10행부터)을
  IT-ID로 갱신한다.
- 파일명은 `test_integration_<통합항목>.py` 형식을 권장한다.

## 10. 작업 절차

1. 입력 아키텍처(`ENG-SWE2-001`, IF-ID·통합 순서)와 관련 요구사항(REQ-ID)·상세설계
   (DES-ID)를 확인한다.
2. §4의 절차대로 통합 순서에 따라 단계별 시험 케이스를 설계한다(§1 기법, §6 케이스 구조).
3. §3의 `measure_call_coverage.py`로 함수/Call 커버리지를 측정하고, 100%가 될 때까지
   케이스를 보완한다.
4. §8에 따라 통합시험 코드를 작성하고, §9에 따라 추적 태그와 `ENG-TRC-001`의 SWE.5 열을
   갱신한다.
5. §5/§7의 문서 구조로 통합전략·시험 명세서, 결과서를 정리한다.
6. 근거 없는 커버리지 수치, 결과, 매핑 관계를 지어내지 않는다. 확인이 필요한 항목은
   "확인 필요"로 표시하고 사용자에게 질문한다.
