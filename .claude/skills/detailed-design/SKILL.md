# SW 상세설계 스킬

이 스킬은 **SW 상세설계(SWE.3)** — 아키텍처 요소를 실제 구현 단위(모듈/클래스/함수)로
분해하고 함수 계약, 알고리즘, 상태전이, 오류처리까지 정의하는 산출물을 작성할 때 따르는
기준과 절차를 정의한다. 시스템/하드웨어 상세설계는 다루지 않는다.

## 1. 적용 표준과 필수 원칙

- **ISO 26262 Part 6**: 상세설계는 단위 수준에서 오류 검출/방어적 프로그래밍, 자원 사용
  한계, 시간 제약을 반영해야 한다.
- **A-SPICE 4.1 SWE.3**: 상세설계는 아키텍처 요소(ARC-ID)를 구현 단위로 완전히 분해하고,
  각 단위가 SW 요구사항과 단위시험(SWE.4)까지 추적 가능해야 한다.
- **아키텍처 원칙의 하향 적용**: `architecture-design` 스킬에서 정한 응집도/결합도, SOLID,
  인터페이스 통신 원칙을 함수/모듈 수준까지 이어간다.
  - 각 함수/모듈은 단일 책임을 갖는다(SRP를 함수 단위로 적용).
  - 함수 계약(입력/출력/사전조건/사후조건)이 곧 모듈 간 "인터페이스"다 — 계약에 없는
    부작용(숨은 전역 변경, 문서화되지 않은 예외)으로 통신하지 않는다.
  - 공통 자료형·상태는 소유 모듈을 명확히 하고, 다른 모듈이 직접 내부 상태를 변경하지
    않는다(캡슐화).
  - 순환 호출을 만들지 않는다 — 호출관계 다이어그램(§3)으로 확인한다.

## 2. 구현 단위 ID와 아키텍처 연계

- 아키텍처 요소(`ARC-<영역>-<일련번호>`)를 구현 단위로 분해하고, 각 단위에
  `DES-<영역>-<일련번호>`(예: `DES-SWE-001`) ID를 부여한다.
- 하나의 아키텍처 요소가 여러 구현 단위로 분해될 수 있다 — 분해 근거(책임 분리 기준)를
  §4의 "2. 모듈 분해"에 기록한다.
- 아키텍처 인터페이스 명세(architecture-design 스킬 §3)에 정의된 제공/요구 인터페이스를
  실제 함수 시그니처로 구체화한다 — 아키텍처 인터페이스와 상세설계 함수 계약이 서로 어긋나면
  안 된다.

## 3. UML 및 호출관계 다이어그램 (TPL-SWE3-002)

`TPL-SWE3-002`의 안내 도형(시스템/설계 경계, 액터, 요소, 관계)을 삭제하고 다음을 채운다:
구현 단위와 책임, 함수 또는 클래스 호출 관계, 입력/출력 자료형, 설계 및 시험 추적 ID.
클래스 다이어그램, 시퀀스 다이어그램 등 필요한 UML 뷰를 함께 첨부할 수 있다(PlantUML/
Mermaid로 텍스트화 후 drawio에 반영).

## 4. 산출물 구조 (TPL-SWE3-001 템플릿 그대로)

1. 목적 및 적용범위 (1.1 목적 / 1.2 적용범위 / 1.3 적용 경계)
2. 모듈 분해 — 아키텍처 요소 → 구현 단위 ID/책임/소스 위치
3. 상세 호출관계 — 함수/클래스 간 호출 순서, 의존 방향, 주요 데이터 흐름 (§3 다이어그램 대응)
4. 공통 자료형 — 데이터 구조, 열거형, 단위, 범위, 불변조건, 직렬화 규칙
5. 핵심 함수 계약 — 함수별 입력/출력/사전조건/사후조건/부작용/예외/시간 제약
6. 핵심 알고리즘 — 처리 순서, 판단 조건, 경계값, 계산 근거 (의사코드 또는 흐름도)
7. 정책 의사결정표 — 입력 조건 조합, 우선순위, 기대 동작, 충돌 해결 규칙
8. 상태전이 상세 — 상태 저장 위치, 전이 함수, 이벤트, 가드, 타이머, 초기화 동작
9. Web 및 API 상세 — 엔드포인트, 요청/응답 구조, 검증, 오류 코드, 세션/보안 경계 (해당 시)
10. 오류와 방어 동작 — 유효하지 않은 입력/예외/자원 실패의 검출·처리·기록·복구
11. 코딩 및 검증 규칙 — 코딩 표준, 정적분석, 단위검증, 커버리지, 리뷰 기준
12. 단위와 요구사항 할당 — 구현 단위 ↔ 아키텍처 요소 ↔ SW 요구사항 ↔ 단위시험 매핑
13. 구현 경계 — 생성 코드, 외부 라이브러리(§0 `TPL-SBOM-001` 참조), 플랫폼 종속부, 구현 제외 범위
14. 추적성 — 아키텍처, 상세설계, 소스 파일, 함수, 단위시험 간 양방향 연결 (§5 대응)
15. 참고자료 — 아키텍처 설계서, 코딩 규칙, API 문서, 외부 라이브러리 자료

## 5. 추적성

- `ENG-TRC-001_양방향 요구사항 추적 매트릭스`(`TPL-TRC-001`)의 **Detailed Design** 열에
  구현 단위(DES-ID) 매핑을 채운다. 이 매트릭스는 Upper Req/SW Req/Architecture/Detailed
  Design/Code/SWE.4/SWE.5/SWE.6/Coverage 열로 구성되며, 데이터는 10행부터 입력한다.
- 각 구현 단위는 최소 하나의 ARC-ID(아키텍처 요소)와 하나 이상의 REQ-ID(요구사항)에
  연결되어야 한다. 연결되지 않는 단위(고아 단위)가 있으면 §4의 "13. 구현 경계"나 "8. 분석
  결과와 가정"에 사유를 남긴다.
- 코드(Code)·단위시험(SWE.4) 열은 구현/단위시험 산출물이 나온 뒤 갱신한다 — 상세설계
  시점에는 계획된 시험 방법과 커버리지 기준(§4의 "11. 코딩 및 검증 규칙")을 남겨 SWE.4
  단계에서 채울 수 있게 한다.

## 6. 작업 절차

1. 입력 아키텍처(ARC-ID, `ENG-SWE2-001`/`002`)와 관련 요구사항(REQ-ID)을 파악한다.
2. §2에 따라 아키텍처 요소를 구현 단위(DES-ID)로 분해하고 분해 근거를 기록한다.
3. §3 다이어그램으로 호출관계를 시각화하고 순환 호출이 없는지 확인한다.
4. §4의 문서 구조에 따라 공통 자료형, 함수 계약, 알고리즘, 정책 의사결정표, 상태전이,
   오류/방어 동작, 코딩·검증 규칙을 작성한다 — 함수 계약 작성 시 §1의 원칙(단일 책임,
   계약 기반 통신, 캡슐화)을 점검한다.
5. §5에 따라 `ENG-TRC-001`의 Detailed Design 열을 갱신한다.
6. 근거 없는 알고리즘 세부사항, 성능 수치, 매핑 관계를 지어내지 않는다 — 확인이 필요하면
   "확인 필요"로 표시하고 사용자에게 질문한다.
