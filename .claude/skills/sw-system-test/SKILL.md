# SW 시스템 테스트 케이스 생성

## 개요

SW 요구사항 명세서 기반으로 SW 시스템 테스트 케이스를 생성하기 위한 방법론 스킬입니다. 이 스킬은 "무엇을 근거로, 어떤 기법으로, 어떤 원칙으로" 테스트 케이스를 설계할지에 대한 방법론만 정의합니다. 요구사항 분석, 사용자와의 확인, 실제 산출물(xlsx) 작성은 이 스킬을 사용하는 에이전트(예: `sw-system-tester` 서브에이전트)가 수행합니다.

**A-SPICE 프로세스 매핑(명확화)**: 이 스킬이 다루는 활동은 통합된 SW 전체를 SW 요구사항
명세서(`ENG-SWE1-001`) 기준으로 블랙박스 검증하는 **A-SPICE SWE.6(소프트웨어 검증)**
활동이다. HW를 포함한 시스템 전체를 시스템 요구사항 기준으로 검증하는 **SYS.5(시스템
시험)**가 아니다 — "시스템 테스트"라는 이름 때문에 혼동하기 쉬우므로 명시한다. `SWE.4`
(단위, `tdd`/`coding`)·`SWE.5`(통합, `integration-testing`/`integration-tester`)와
구분되는 지점은 **시험 근거가 DES-ID나 인터페이스(IF-ID)가 아니라 SW 요구사항(REQ-ID)
전체이고, 화이트박스가 아니라 블랙박스라는 것**이다.

## 산출물 템플릿과 적용 범위 (필수 준수)

이 저장소의 `WP_Templates/Engineering/SoftwareVerification/`에 있는 템플릿을 **그대로**
따른다. 새로운 시트/열 구조를 임의로 만들지 않는다.

| Template ID | 파일 | 용도 |
|---|---|---|
| `TPL-SWE6-001` | `SW 검증 명세서 템플릿.xlsx` | 테스트 케이스 명세 구조 (아래 "산출물 구조" 참고) |
| `TPL-SWE6-002` | `SW 검증 결과서 템플릿.xlsx` | 실행 결과 구조 — 이 스킬은 케이스 설계까지만 다루고, 결과서 작성은 실행을 담당하는 별도 활동(사용자 또는 향후 에이전트)의 몫이다 |

`ENG-SWE6-002_SW 검증 결과서.xlsx`.

> **교육용 자료 안내**: 이 저장소는 교육용 가상 프로젝트(VJ-ECL-2026)이며
> (`WP_Templates/PRC-TPL-001_표준 산출물 양식 등록부.xlsx` 명시), PC/SIL·Web 증거만
> 다루고 **HIL, 실차, 시스템 시험, 공식 A-SPICE 심사, ISO 26262 준수, 인증 또는 ASIL
> 달성을 주장하지 않는다**. 이 스킬로 작성하는 테스트 케이스도 실제 인증·준수를
> 주장하지 않는다.

## 기반지식

- **ISO 26262 Part 6**: 소프트웨어 단위/통합/시스템 테스트에 대한 요건. 특히 ASIL 등급이 할당된 요구사항은 판정기준의 전 분기(경계값, 조건 조합)를 빠짐없이 검증해야 합니다.
- **A-SPICE SWE.4, SWE.5, SWE.6**: 소프트웨어 단위 검증, 통합 시험, 시스템 시험에 대한 Base Practice. 양방향 추적성(요구사항 ↔ 테스트 케이스)과 표준화된 시험 절차를 요구합니다.
- **ISO 29119 및 ISTQB**: 테스트 시나리오·테스트 케이스 설계 프로세스와 용어 체계(긍정/부정 분류 등)의 근거로 사용합니다.
- **ISO 25000 (SQuaRE)**: 비기능(품질) 요구사항을 분류하는 기준입니다. `requirements-analysis` 스킬이 REQ 작성 시 사용하는 것과 동일한 ISO 25010 품질 특성(기능 적합성, 성능 효율성, 호환성, 사용성, 신뢰성, 보안성, 유지보수성, 이식성)별로 비기능 테스트 케이스를 그룹화합니다.

## 적용 대상 테스트 기법

**`integration-testing` 스킬과의 관계**: `integration-testing` 스킬의 ISO 26262 Part 6
"시험 방법"(요구사항 기반 시험, 인터페이스 시험, 결함 주입 시험 등)은 *어떤 종류의 검증
활동을 할 것인가*를 정하는 상위 개념이고, 아래 목록은 *그 시험의 구체적인 입력값을 어떻게
도출할 것인가*를 정하는 테스트 케이스 설계 기법이다. 이 스킬에서는 "요구사항 기반 시험"이
기본 시험 방법이며, 아래 기법으로 그 시험의 케이스를 도출한다 — 두 스킬이 같은 용어를
다른 계층에서 쓰고 있으니 혼동하지 않는다.

요구사항의 성격에 맞춰 아래 기법 중에서 선택하여 적용하고, 각 테스트 케이스의 "사용 기법" 항목에 실제로 적용한 기법을 명시합니다.

- **경계값 분석**: 검증기준에 수치·범위·임계값이 있는 경우, 경계값 미만/경계값/경계값 초과를 각각 별도 케이스로 도출합니다.
- **동치 클래스(동등분할)**: 입력 도메인을 유효/무효 클래스로 나누어 대표값을 도출합니다.
- **조합 테스트(전 조건 조합)**: 관련 조건 수가 적어 전수 조합이 실행 가능한 범위일 때 우선 적용합니다.
- **페어와이즈**: 조건·값의 조합 수가 많아 전수 조합 테스트가 비현실적인 경우에 대체 적용합니다.
- **엣지 케이스**: 정상 범위의 극단, 동시성/타이밍 등 일반 분석 기법으로 포착되지 않는 특이 조건을 다룹니다.
- **경험 기반 테스트**: 유사 시스템의 결함 이력이나 QA 경험에 근거해 오류를 추정합니다(오류 추정, 탐색적 테스트 등).

## 작성 원칙

- 의미 없이 테스트 커버리지 수치 달성만을 목적으로 하는 케이스는 생성하지 않습니다.
- 테스트의 예상 결과를 임의로 가정하지 않습니다. 명세서에 근거가 없다면 이 스킬을 사용하는 에이전트가 사용자에게 확인을 받아야 합니다.
- 이 스킬의 커버리지 목표는 요구사항 커버리지 100%다(위 "커버리지와 추적성" 참고).
  CLAUDE.md "통합시험 지침"의 함수/Call 커버리지 100%는 `integration-testing`(SWE.5)
  전용 지표이며 이 스킬에는 적용하지 않는다.
- 실행자가 그대로 재현할 수 있는, 실행 가능한 테스트 케이스만 작성합니다.
- 기법 선택이나 커버리지 범위 설정이 판단하기 어려운 경우 임의로 결정하지 말고, 이 스킬을 사용하는 에이전트를 통해 사용자 검토를 받습니다.
- 명세서에 직접적 근거는 없으나 QA 관점에서 추가를 제안하고 싶은 테스트 케이스는 테스트 케이스명 끝에 "(제안)"이라고 표시해 구분합니다.
- 사용한 테스트 설계 기법을 각 케이스에 명시합니다.

## 도구 사용

- 페어와이즈 조합을 생성할 때는 오픈소스인 PICT를 사용합니다.
- 전수 조합(모든 조건의 조합)을 생성할 때는 PICT의 `/o:max` 옵션을 사용합니다.

## 산출물 구조 (TPL-SWE6-001 템플릿 그대로 — 시트/열 이름을 임의로 바꾸지 않는다)

`TPL-SWE6-001`은 시트 하나(`Verification Specification`)에 다음 열을 가진다(데이터는
10행부터): **Test ID | SW Req | Level/Environment | Stimulus | Expected Result |
Technique | Execution**. 기능/비기능 요구사항을 별도 시트로 나누지 않고, 같은 시트 안에서
`SW Req`(REQ-ID)로 구분한다 — 비기능 요구사항의 테스트 케이스는 그 REQ-ID가 속한
`requirements-analysis`의 ISO 25010 품질 특성을 `SW Req` 옆에 괄호로 병기하거나
`Level/Environment` 열에 함께 적어 구분한다(예: `REQ-SWE-010 (신뢰성)`).

이 스킬에서 추가로 요구하는 아래 내용은 템플릿에 없는 보충 정보이므로, 템플릿의 7개 열을
**유지한 채** 오른쪽에 열을 추가해 기록한다(열 구조를 대체하지 않는다):

- **테스트 케이스 ID 체계**: `QT-<영역>-<일련번호>`(예: `QT-SWE-001`) — A-SPICE SWE.6
  ("Software **Q**ualification **T**est")임을 나타내며 `SYS.5`(시스템 시험)와 구분한다.
  `Test ID` 열 값으로 이 형식을 사용한다.
- **확정 근거 열(추가)**: 요구사항 원문에 없거나 원문보다 엄격한 판정기준을 사용자 확인을
  거쳐 확정한 경우, 확정 일자와 승인 주체를 기록한다.
- **제안 표시**: 명세서에 직접적 근거는 없으나 QA 관점에서 추가를 제안하는 케이스는
  `Test ID` 또는 케이스명 끝에 "(제안)"을 표기한다(에이전트 업무지침과 동일).

## 커버리지와 추적성

- 이 스킬의 커버리지 목표는 **요구사항 커버리지 100%**다 — SW 요구사항 명세서의 모든
  REQ-ID(기능·비기능)가 최소 1개 이상의 테스트 케이스(`SW Req` 열)에 연결되어야 한다.
  **`integration-testing` 스킬의 함수/Call 커버리지(코드 구조 커버리지, SWE.5 전용
  지표)와는 다른 지표이므로 섞어 쓰지 않는다.**
- `ENG-TRC-001_양방향 요구사항 추적 매트릭스`(`TPL-TRC-001`)의 **SWE.6** 열(10행부터)을
  `QT-ID`로 갱신한다.
- CLAUDE.md "시스템 테스트(검증, SWE.6) 지침"은 **테스트 성공률 100%**도 요구한다. 이
  스킬은 케이스 설계까지만 다루므로(§0), 실행은 사용자/향후 에이전트의 몫이지만 각 케이스의
  `Expected Result`가 명확해 실행 시 통과/실패 판정이 모호하지 않도록 작성한다.
